Below is an implementation-ready architecture/design document. I’ve made it intentionally explicit about components, responsibilities, data flow, APIs, agent behavior, schemas, folder structure, and development phases, so you can paste it into another LLM and ask it to start building the project.

Agentic ML Model & Dataset Evaluation Platform
Design and Architecture Specification

Document Version: 1.0
Purpose: Implementation specification for an LLM/code-generation agent
Primary LLM Runtime: Ollama
Available Local Models: Phi-3 Mini and Llama 3.1
Backend: Python
Database / Project Memory: ChromaDB
Primary Interface: Chatbot / conversational UI
Architecture Style: Agentic tool-calling workflow

1. Project Objective

Build an agentic machine-learning evaluation platform where a user can:

Upload an ML model.
Upload a dataset.
Ask questions or give objectives through a chatbot.
Allow an AI agent to inspect the model and dataset.
Automatically determine what operations are required.
Evaluate the dataset and model.
Detect problems such as:
missing values
class imbalance
outliers
incorrect feature types
incompatible input shapes
poor model performance
robustness problems
Apply appropriate data transformations when necessary.
Re-run model evaluation after transformations.
Compare the original and transformed results.
Maintain experiment history.
Generate a final natural-language evaluation report.

The central design principle is:

The model and dataset are the center of the workflow. The agent continuously decides what should happen to them based on the user's goal and the results of previous operations.

The system must therefore behave as an agentic decision-making system, rather than a simple sequence of API calls.

2. Core Architectural Principle

The architecture must NOT be designed as:

User
  ↓
API
  ↓
Function
  ↓
Result


Instead, it must follow:

USER GOAL
    ↓
AGENT
    ↓
UNDERSTAND OBJECTIVE
    ↓
INSPECT MODEL + DATASET
    ↓
SELECT TOOL
    ↓
EXECUTE TOOL
    ↓
OBSERVE RESULT
    ↓
REASON
    ↓
DECIDE NEXT ACTION
    ↓
SELECT NEXT TOOL
    ↓
EXECUTE
    ↓
OBSERVE
    ↓
REASON
    ↓
...
    ↓
SUFFICIENT RESULT?
    ├── YES → GENERATE REPORT
    │
    └── NO → CONTINUE AGENT LOOP


The agent is responsible for deciding what happens next.

4. Main Components

The system consists of the following major components.

4.1 Frontend

Responsibilities:

Upload model
Upload dataset
Create/select project
Start evaluation
Chat with agent
Display agent actions
Display evaluation results
Display experiment history
Display before/after comparisons
Display final report

The frontend should NOT contain ML evaluation logic.

5. Backend

Recommended framework:

FastAPI


The backend provides REST APIs for:

/projects
/models
/datasets
/evaluations
/experiments
/chat
/reports


The backend coordinates the frontend, agent, ML tools, storage and database.

6. Agent

The agent is the most important component of the architecture.

The agent should be implemented as a stateful loop.

Agent responsibilities

The agent must:

Understand the user's goal.
Inspect available project resources.
Determine the current state.
Select an appropriate tool.
Execute the tool.
Observe the tool result.
Store the result.
Reason about the result.
Determine whether another action is necessary.
Select the next action.
Repeat until the objective is satisfied.
Generate a final response/report.
7. Local LLM Architecture

Ollama will be used as the local model runtime.

The system should support:

Ollama
 ├── Phi-3 Mini
 └── Llama 3.1


The application should NOT hard-code one model throughout the codebase.

Create a model configuration:

LLM_MODEL=llama3.1
OLLAMA_BASE_URL=http://localhost:11434


The configuration should allow switching to:

phi3


without changing application code.

8. Agent vs Evaluation LLM

There should be a clear distinction between:

Agent / Planner

Responsible for:

What should I do next?

Evaluation Model / LLM

Responsible for:

What do these results mean?


These should not be confused.

The numerical calculations must be performed by deterministic Python functions.

The LLM should interpret those results.

For example:

Python:
accuracy = 0.92
f1 = 0.87
class_imbalance = 0.72

        ↓

LLM:

"The dataset has substantial class imbalance and the
model's minority-class performance should be investigated."


The LLM must NOT invent the numerical metrics.

9. Tool Architecture

The agent should interact with the system through tools.

Every tool should have:

name
description
input schema
output schema
implementation


The agent should never directly manipulate files or datasets through arbitrary generated Python code unless explicitly designed as a controlled sandbox.

14. Evaluation Functions

Evaluation functions produce objective technical results.

These functions must be deterministic wherever possible.

Create:

evaluate_performance()
evaluate_data_quality()
evaluate_robustness()
evaluate_transformation_impact()

15. Performance Evaluation

The system should select metrics based on task type.

For classification:

accuracy
precision
recall
F1
confusion matrix
ROC-AUC where applicable
PR-AUC where applicable
per-class metrics


For regression:

MAE
MSE
RMSE
R²
MAPE where appropriate


The exact metrics should be configurable.

The agent should not blindly use accuracy for every problem.

16. Data Quality Evaluation

The data-quality evaluator should detect:

missing values
duplicate rows
invalid values
incorrect data types
class imbalance
constant columns
near-constant columns
outliers
unexpected categories
high-cardinality categorical features


Output example:

{
  "missing_values": {
    "status": "warning",
    "count": 324
  },
  "class_imbalance": {
    "status": "problem",
    "ratio": 4.55
  },
  "duplicates": {
    "status": "warning",
    "count": 27
  }
}

17. Robustness Evaluation

Robustness tests should measure how model performance changes when the input data is altered.

Examples:

Gaussian noise
missing values
outliers
label noise
feature perturbation


The system should preserve the original dataset.

Never overwrite the original dataset during experiments.

18. Transformation Functions

Transformation functions actually modify the dataset.

Create two categories.

Data Improvement
clean_data()
scale_data()
handle_outliers()
balance_data()
handle_missing_values()
encode_categorical_features()

Data Corruption
add_gaussian_noise()
inject_missing_values()
inject_outliers()
inject_label_noise()


Each transformation must create a new dataset version.

Example:

dataset_original
       ↓
dataset_v001_cleaned
       ↓
dataset_v002_scaled
       ↓
dataset_v003_balanced

19. Dataset Versioning

Dataset versioning is critical.

Never modify:

original_dataset.csv


Instead:

datasets/
    original/
        dataset.csv

    versions/
        v001/
            dataset.csv
            metadata.json

        v002/
            dataset.csv
            metadata.json


Every transformation must record:

{
  "version": "v002",
  "parent_version": "v001",
  "operation": "balance_data",
  "parameters": {
    "method": "smote"
  },
  "created_at": "...",
  "rows_before": 10000,
  "rows_after": 15000
}

20. The Agentic Loop

The core agent loop should conceptually work like this:

while not state.is_complete():

    context = build_agent_context(state)

    decision = agent.decide(context)

    tool = decision.tool

    result = execute_tool(
        tool,
        decision.parameters
    )

    state.add_observation(result)

    state.record_action(
        tool=tool,
        result=result
    )

    if decision.is_complete:
        break


The actual implementation should include:

maximum iteration count
error handling
tool validation
state persistence
timeout handling
user cancellation

The agent should maintain explicit state.

Example:

{

  "user_goal": "Evaluate the model and improve performance",

  "model": {
    "id": "model_001",
    "status": "loaded"
  },

  "dataset": {
    "current_version": "v002"
  },

  "observations": [],

  "actions": [],

  "evaluation_results": [],

  "transformations": [],

  "iteration": 3,

  "status": "running"
}


Do not rely exclusively on the LLM's conversation history as state.

The application should maintain structured state.

23. Important Agent Rule

The agent must NOT automatically perform every available transformation.

Bad architecture:

Clean
↓
Scale
↓
Balance
↓
Noise
↓
Outliers
↓
Everything


Correct architecture:

Observe
↓
Identify problem
↓
Determine whether action is appropriate
↓
Choose transformation
↓
Evaluate
↓
Compare
↓
Decide whether another action is needed


This prevents unnecessary transformations.

27. LLM Safety / Reliability Rule

The LLM should never be the source of truth for numerical results.

For example, the LLM must not calculate:

accuracy
F1
RMSE
missing-value percentage
class ratios


when Python can calculate them.

Correct:

Python calculates
       ↓
structured JSON result
       ↓
LLM interprets


Incorrect:

Dataset
       ↓
LLM guesses statistics

WHAT should happen next?

Performs:

HOW the operation is executed.

Calculates:

WHAT are the objective results?

Transformation

Changes:

THE DATASET

Stores:

WHAT HAPPENED BEFORE?

Evaluation LLM

Explains:

WHAT DO THE RESULTS MEAN?

API

Provides:

HOW DOES THE USER/FRONTEND ACCESS THE SYSTEM?

33. Tool Selection

The LLM should return structured decisions.

Example:

{
  "action": "evaluate_data_quality",
  "reason": "The dataset needs to be inspected before evaluating transformations.",
  "parameters": {
    "dataset_version": "v001"
  }
}


Another example:

{
  "action": "balance_data",
  "reason": "Severe class imbalance was detected and minority-class performance is poor.",
  "parameters": {
    "dataset_version": "v001",
    "method": "smote"
  }
}


The backend validates this decision before executing the tool.

34. Do Not Trust LLM Tool Parameters Blindly

Every tool call must be validated.

For example, if the LLM returns:

{
  "action": "balance_data",
  "dataset_version": "does_not_exist"
}


the backend must reject it.

The agent should receive:

Tool execution failed:
Dataset version does not exist.
Available versions: v001, v002.


The agent can then decide what to do next.

This is part of the agentic loop.

Agent determines preprocessing mismatch
 ↓
Agent decides next action


Do not simply terminate the entire workflow for recoverable errors.

36. Agent Stopping Conditions

The agent must stop when:

User objective has been satisfied


or:

No useful action remains


or:

Maximum iterations reached


or:

Required resource is unavailable


or:

Human approval is required


Example:

MAX_AGENT_ITERATIONS=10


This prevents infinite loops.

37. Human Approval

For destructive or expensive operations, the agent should request confirmation.

For example:

The agent recommends balancing the dataset using SMOTE.

This will create a new dataset version containing synthetic samples.

Proceed?


The original dataset must remain untouched regardless.

48. Data Leakage Prevention

This is extremely important.

Transformations such as:

imputation
SMOTE

must be fitted only on the training data where appropriate.

The architecture should distinguish:

test


The test set should not be used to tune transformations.

The agent should not be allowed to accidentally optimize against the test set repeatedly.

67. Critical Design Rules

The implementation must follow these rules.

Rule 1

Original datasets are immutable.

Rule 2

Every transformation creates a new dataset version.

Rule 3

Every evaluation produces structured machine-readable results.

Rule 4

Numerical metrics are calculated by Python, not the LLM.

Rule 5

The LLM interprets results and decides actions.

Rule 6

The agent decides dynamically what tool should run next.

Rule 7

The agent must observe tool results before deciding the next action.

Rule 8

Previous experiments must influence future decisions.

Rule 9

The system must have an explicit stopping condition.

Rule 10

The agent must not repeatedly apply transformations without evidence that they are useful.

Rule 11

Baseline results must always be preserved.

Rule 12

The user must be able to see a concise description of the agent's actions.

71. Final Architectural Principle

The most important concept in this project is that the agent is not the center of the data itself.

The center is:

              ┌───────────────┐
              │     MODEL     │
              └───────┬───────┘
                      │
                      ↕
              ┌───────────────┐
              │    DATASET    │
              └───────┬───────┘
                      │
                      ▼
              ┌───────────────┐
              │  EVALUATION   │
              └───────┬───────┘
                      │
                      ▼
              ┌───────────────┐
              │    RESULTS    │
              └───────┬───────┘
                      │
                      ▼
                 ┌─────────┐
                 │  AGENT  │
                 └────┬────┘
                      │
              DECIDES NEXT ACTION
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
    TRANSFORM DATA           RUN EVALUATION
          │                       │
          └───────────┬───────────┘
                      ▼
                NEW RESULTS
                      │
                      ▼
                    AGENT
                      │
               DECIDE AGAIN
                      │
                     ...


The agent therefore operates as a closed-loop controller around the model, dataset, evaluation system, and project memory.

The fundamental workflow is:

USER GOAL
   ↓
AGENT
   ↓
INSPECT
   ↓
ACT
   ↓
OBSERVE
   ↓
EVALUATE
   ↓
REASON
   ↓
ACT AGAIN
   ↓
OBSERVE
   ↓
COMPARE
   ↓
DECIDE
   ↓
FINISH


This is what makes the application genuinely agentic.
