### Execution Rules & Constraints

1. **State Isolation:** Narrow requests (e.g., `Inspect my model`) execute only required tools and terminate immediately without triggering full evaluation.
2. **Raw Dataset Authority:** Evasion attacks (`fgsm`, `pgd`, `cw`, `boundary_attack`, `hopskipjump`, `zoo`) and ART defenses evaluate against the raw baseline dataset (`v001`) to assess true model vulnerability rather than pre-transformed representations.
3. **Subsampled Fast Execution:** Adversarial attacks and defenses run on a stratified, seeded sample ($n = 30$) across original target classes, ensuring evaluation completes quickly while maintaining statistical balance. Note the granularity: each percentage moves in ~3.3-point steps, so differences under ~10 points are noise at this sample size.
4. **Float32 Tensor Enforcers:** Features transformed by ART preprocessors are explicitly cast to `np.float32` before prediction passes, preventing PyTorch `Double` vs `Float` matrix multiplication type mismatches (`mat1 and mat2`).
5. **Universal Hyperparameter Injection:** User prompts containing explicit hyperparameter overrides (e.g., `eps=0.25`, `max_iter=15`, `sigma=1.2`, `bit_depth=4`) are extracted via regex and injected into `AgentState` before tool execution.
6. **Deterministic Security Planning:** Compound security operations (sweep, hardening loop, harden model) are pinned to deterministic planning. They are never delegated to free-form LLM planning because they have strict legal ordering and metric dependencies.

### Completion / Finalization Gate

A workflow that still needs to persist or report must **not** be finalized just because its core tool succeeded. `AgentRunner._can_finalize_after_successful_action` keeps these actions running until `save_experiment` has actually run:

`attack_defended_model`, `defended_attack`, `harden_model`, `harden`, `hardening_loop`, `harden_defense_loop`.

Omitting a workflow from this allowlist causes its results to be silently dropped (the run ends before persistence), which is the single most likely reason a graph appears empty after a successful run.

## 4. Autonomous Agent Architecture & Capability Report

### Agent Architecture Overview

The system uses **1 Centralized Autonomous Agent** implemented across two Python classes bound by an `AgentState` context:

1. **`AgentPlanner` (Brain):** Receives state summaries and prompt directives, invokes the Groq-hosted LLM for next-step planning, or runs deterministic fallback logic when state transitions are strictly governed (security workflows). Also builds multi-step series for persistence.
2. **`AgentRunner` (Executor/Driver):** Manages the loop iteration, executes Python tools via `ToolRegistry`, enforces the finalization gate, handles failures, updates `AgentState`, persists records, and calls report generators.

```
                     +-----------------------------------+
                     |            AGENT STATE            |
                     | - Execution Flags                 |
                     | - Evaluated Versions              |
                     | - Metrics & Observations          |
                     | - Compatibility Result (True/False)|
                     +-----------------+-----------------+
                                       |
                     +-----------------+-----------------+
                     |                                   |
                     v                                   v
          +---------------------+             +---------------------+
          |    AGENT PLANNER    |             |    AGENT RUNNER     |
          |  (Decision Engine)  |             |  (Driver Loop)      |
          | - Prompt Analysis   |             | - Tool Execution    |
          | - Action Validation |             | - Finalization Gate |
          | - Fallback Routing  |             | - Error Catching    |
          | - Series Building   |             | - State Mutation    |
          +---------------------+             +---------------------+
```

1. **Model & Dataset Inspection Tools**
* `inspect_model`: Extracts framework, architecture, input/output shapes, layer dimensions, parameter counts.
* `inspect_dataset`: Profiles rows, columns, feature types, missingness, duplicates, target distribution.
* `validate_model_dataset`: Checks feature dimension compatibility and class label alignments.

2. **Evaluation & Quality Benchmarks**
* `evaluate_performance`: Computes Accuracy, Precision Macro, Recall Macro, Macro F1, Minority F1, RMSE.
* `evaluate_data_quality`: Audits missing ratios, class imbalance ratios, outlier counts, constant columns.
* `evaluate_robustness`: Measures accuracy degradation under Gaussian feature noise perturbations.

3. **Adversarial Security Tools (ART Integration)**
* `fgsm`, `pgd`, `cw`: Gradient-based evasion attacks for PyTorch neural models.
* `boundary_attack`, `hopskipjump`, `zoo`: Black-box/decision-based evasion attacks for Tree/Ensemble and non-differentiable models.
* `gaussian_augmentation`, `spatial_smoothing`, `feature_squeezing`, `clip_values`: Preprocessor input defenses.
* `reverse_sigmoid`, `class_labels`, `high_confidence_masking`: Postprocessor logit/probability defenses.

4. **Multi-Step Security Operations**
* `attack_defended_model`: Independent attack+defense measurement against one model (used by the comparative sweep).
* `harden_model`: Single-round adversarial retraining (attack then retrain).
* `harden_defense_loop`: Cumulative hardening loop; each round attacks the *current* model, retrains it, and feeds the retrained model into the next round. Only the final hardened model is registered as an asset.

5. **Data Engineering & Transformation Tools**
* `handle_missing_values`, `balance_data` (SMOTE/Sampling), `handle_outliers` (Clipping/Removal), `scale_data` (Standard/MinMax).
* `add_gaussian_noise`, `inject_missing_values`, `inject_label_noise`: Data stress-testing corruptions.

6. **Persistence, Memory & Synthesis Tools**
* `save_experiment`: Writes experiment parameters and comparisons (including multi-step `series`) to SQLite and ChromaDB vector store.
* `compare_results`: Calculates programmatic before-vs-after delta metrics across dataset versions.
* `search_project_history`: Performs semantic vector searches over past project runs.
* `generate_report`: Compiles structured evaluation metrics into a Markdown diagnostic report.

## 5. Multi-Step Security Workflows

### 5.1 Comparative Attack / Defense Sweep (up to 5 combinations)

Prompt pattern:
`compare fgsm, pgd and cw with feature_squeezing and generate a report`

* Each combination is an **independent** measurement against the same unmodified model. The defense is an input preprocessor and is **not written back**, so combinations do not stack.
* Persists operation `attack_defense_sequence_N`.
* Persists `comparison.series` with `kind: "sweep"` and one item per combination.
* Report section 8.3 covers the sweep.
* UI renders grouped bars per combination from the persisted series.

### 5.2 Cumulative Adversarial Hardening Loop (up to 5 rounds)

Prompt pattern:
`harden my model over 5 rounds against fgsm, pgd, hopskipjump and zoo with feature_squeezing using pgd`

* Each round attacks the **current** model, adversarially retrains it, and feeds the retrained model into the next round. Robustness genuinely accumulates.
* Intermediate rounds retrain with `persist=False`; only the final hardened model is registered as an asset.
* Persists operation `hardening_loop_N_rounds`.
* Persists `comparison.series` with `kind: "loop"` and one item per round. Each item carries its own `model_id` so a reader can tell which artefact produced which number.
* Report section 9 covers the loop.
* **Mixed-threat curricula** are supported: a named list of attacks cycles across the rounds (e.g. `fgsm -> pgd -> hopskipjump -> zoo -> fgsm` for 5 rounds). A first-to-final delta is only reported when every round measured the same attack; otherwise it is reported per attack.

`N` is user-supplied, defaults to 2, hard cap 5, and is an upper bound only. Combinations/rounds are never duplicated or invented to reach `N`.

## 6. Charting & Persistence

* Experiments are stored in SQLite; `comparison` blobs are JSON and may carry a `series` object:

```json
{ "kind": "sweep" | "loop", "count": <int>, "items": [ ... ] }
```

* Series values are copied from evaluator output, **never recomputed**, so a chart cannot disagree with the report.
* Absent metrics are omitted, never rendered as zero.
* Chart views:
  * **Noise / Attacks / Defenses** — existing 3-series comparison bar chart.
  * **Sweep** — grouped bars, one group per combination.
  * **Loop** — per-round points. A line is drawn only when every round measured the same attack. In a mixed-threat run the rounds are rendered as **unconnected points** (all values still shown) so the chart does not imply a trend the numbers do not support. Tick labels name the attack for each round.
* All views share one canvas region. A small canvas-ownership registry (`releaseChartCanvas` / `claimChartCanvas`) releases the previous chart before a new view claims it. `claimChartCanvas` takes a **thunk** (a factory function), not a chart instance, because JS evaluates arguments before the call — passing `new Chart(...)` directly would construct the chart before the release and throw `Canvas is already in use`.
* **No retroactive repair:** historical experiments without a series render as a single point until the workflow is re-run.

## 7. Safety Guardrails & Operational Constraints

* **Strict Action Legality Gate (`AgentPlanner._is_action_legal`):** Prevents executing illegal tool sequences (e.g., attempting `balance_data` before dataset compatibility validation).
* **Finalization Gate:** A workflow needing persistence/reporting is not finalized until `save_experiment` has run (see Section 2). This is the single place where a missing allowlist entry silently drops results.
* **Fail-Fast Refusals:** Incompatible model/dataset pairs and unsupported attack/method combinations are refused up front with a user-facing reason, rather than planned and failed after expensive work.
* **Compatibility Gate:** Security actions require a **passed** compatibility check (`compatibility_result is True`), not merely one that ran.
* **Infinite Loop Protection:** Tracks consecutive tool failures (`limit = 3`). If a tool fails repeatedly, execution terminates with status `"failed"` and a real cause.
* **Dataset Immutability:** Transformations never overwrite existing files. New version directories (`v001`, `v002`, `v003`) are created with transformation metadata logs.
* **No Metric Fabrication:** Numerical metrics are generated exclusively by deterministic Python functions. The LLM is restricted to formatting, reasoning, and context analysis.
* **Tensor Serialization Safety:** Large numpy array tensors (`x_adv`, `x_aug`) are removed from state memory before logging to prevent memory bloat, returning JSON-safe `.tolist()` summaries for inspection.
* **Bounded Filenames:** Hardened model file names are length-bounded (existing `hardened_<ts>_` markers are stripped and one is re-applied) so long hardening chains cannot exceed filesystem path limits.
* **Environment / Test Isolation:** `tests/conftest.py` sets `STORAGE_DIR` and `CHROMA_PERSIST_DIR` before any `app` import so tests never touch real storage.
