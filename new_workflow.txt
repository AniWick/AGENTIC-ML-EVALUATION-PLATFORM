================================================================================
AGENTIC ML EVALUATION PLATFORM - SYSTEM & EXECUTION WORKFLOW
============================================================

# Last Updated: 2026-09-04

This document describes the complete architecture, request routing, agent
decision cycle, deterministic evaluation engine, state management, memory,
versioning, and reporting workflow of the Agentic ML Evaluation Platform.

The platform uses a HYBRID AGENTIC ARCHITECTURE:

1. User intent determines WHAT kind of task is being requested.
2. Python determines WHICH operations are legal and authoritative.
3. Qwen assists with intent classification, planning, and natural-language
   reasoning.
4. Deterministic Python tools calculate all metrics and perform all mutations.
5. AgentState maintains the authoritative execution state.
6. ChromaDB is used for semantic recall of historical experiments.
7. SQLite remains the authoritative persistent project database.

IMPORTANT ARCHITECTURAL PRINCIPLE:

The full deterministic evaluation pipeline remains available as the reliable
backbone of the system.

However, a narrow informational request MUST NOT automatically trigger the
entire evaluation pipeline.

For example:

```
"Inspect my model and dataset"
    -> inspection flow only

"What were the baseline metrics before any transformation?"
    -> baseline information flow only

"Evaluate my model and dataset"
    -> full deterministic evaluation flow

"Improve my dataset"
    -> evaluation + targeted transformations + re-evaluation

"Did SMOTE help?"
    -> comparison / historical-result flow
```

================================================================================
2. CORE DESIGN PRINCIPLES
=========================

## 2.1 HYBRID AGENTIC CONTROL

The platform is neither:

```
"fully hardcoded"
```

nor:

```
"let the LLM decide everything."
```

Instead:

```
User Request
    |
    v
Intent / Scope Routing
    |
    v
Appropriate deterministic flow
    |
    v
Qwen may recommend the next legal action
    |
    v
Python validates legality
    |
    v
Deterministic tool executes
    |
    v
AgentState is updated
    |
    v
Next decision
```

Python remains authoritative.

Qwen cannot directly execute code, calculate metrics, modify datasets, or
override state-machine restrictions.

## 2.2 DETERMINISTIC TOOLS ARE AUTHORITATIVE

All numerical ML metrics are calculated by deterministic Python components.

The LLM MUST NOT:

* calculate metrics
* guess metrics
* estimate missing metrics
* fabricate experiment results
* invent dataset properties
* claim a transformation improved performance without measured evidence

Examples of deterministic calculations:

* Accuracy
* Precision
* Recall
* Macro F1
* Minority F1
* ROC-AUC
* RMSE
* Confusion Matrix
* Missing-value count
* Imbalance ratio
* Outlier count
* Performance deltas
* Robustness degradation

## 2.3 ORIGINAL DATASET IS IMMUTABLE

The original dataset is never overwritten.

Initial dataset:

```
v001
```

Transformation:

```
v001 -> v002
```

Another transformation:

```
v002 -> v003
```

Every transformed dataset receives a new immutable version.

Each version stores:

```
dataset.csv
metadata.json
```

Metadata records:

* parent version
* operation
* parameters
* creation information

## 2.4 AGENTSTATE IS THE EXECUTION SOURCE OF TRUTH

AgentState maintains the current execution state.

Important fields include:

```
project_id
user_goal
model_id
dataset_id
current_dataset_version

is_model_inspected
is_dataset_inspected
is_compatibility_validated
is_baseline_evaluated
is_data_quality_evaluated
is_robustness_evaluated

model_metadata
dataset_metadata
baseline_metrics
data_quality_metrics
robustness_metrics
latest_metrics

evaluated_dataset_version
transformations_applied
experiments
observations
actions_taken
```

This prevents the planner from treating an old evaluation as the evaluation
of a newer dataset version.

3. REQUEST ROUTING ARCHITECTURE
===============================

Every chat request first enters the Chat Router.

Example:

```
User:
"What were the baseline metrics before any transformation?"
```

The system MUST distinguish between:

```
EXECUTION REQUEST
INFORMATION REQUEST
COMPARISON REQUEST
```

The current intent categories are expanded conceptually into the following
request types:

```
1. INFORMATION
2. SPECIFIC DETERMINISTIC ACTION
3. FULL EVALUATION
4. IMPROVEMENT
5. COMPARISON
6. HISTORICAL / PROJECT MEMORY
```

---

## 3.1 INFORMATION REQUEST

Used when the user wants information that can be answered from current
authoritative state/results.

Examples:

```
"What were the baseline metrics?"
"What is my model accuracy?"
"How many missing values were found?"
"What was the robustness score?"
"Tell me about my model."
"What columns does my dataset have?"
```

The system should retrieve the relevant existing state.

It should NOT automatically execute unrelated evaluation stages.

Example:

```
"What were the baseline metrics?"
```

Expected behavior:

```
If baseline_metrics already exists:
    -> read baseline_metrics
    -> answer user
    -> STOP

If baseline_metrics does not exist:
    -> execute only the minimum deterministic prerequisites
    -> evaluate baseline
    -> answer user
    -> STOP
```

It must NOT automatically continue into:

```
data quality
robustness
transformations
re-evaluation
experiment saving
report generation
```

---

## 3.2 INSPECTION REQUEST

Example:

```
"Inspect my model."
```

Expected:

```
inspect_model
-> answer
-> STOP
```

Example:

```
"Inspect my dataset."
```

Expected:

```
inspect_dataset
-> answer
-> STOP
```

Example:

```
"Inspect my model and dataset."
```

Expected:

```
inspect_model
-> inspect_dataset
-> validate_model_dataset
-> answer
-> STOP
```

The inspection request does NOT imply:

```
baseline evaluation
data-quality evaluation
robustness evaluation
transformations
report generation
```

---

## 3.3 SPECIFIC DETERMINISTIC ACTION

Examples:

```
"Clean the missing values."
"Balance the dataset."
"Apply SMOTE."
"Handle the outliers."
"Scale the dataset."
"Generate the report."
```

The system executes the requested operation and only the necessary
prerequisites.

Example:

```
"Balance the dataset."
```

Possible flow:

```
inspect dataset if required
    ->
evaluate data quality if required
    ->
balance_data
    ->
create new immutable dataset version
    ->
stop unless the user explicitly requested re-evaluation/evaluation
```

If the user explicitly asks:

```
"Balance the dataset and evaluate whether it helped."
```

Then the flow becomes:

```
inspect
-> evaluate
-> balance
-> re-evaluate
-> compare
-> answer
```

---

## 3.4 FULL EVALUATION REQUEST

Examples:

```
"Evaluate my model and dataset."
"Run the full evaluation."
"Perform a complete evaluation."
"Evaluate everything."
```

This activates the complete deterministic agentic workflow.

The full workflow is:

```
STEP 1  -> Inspect Model
STEP 2  -> Inspect Dataset
STEP 3  -> Validate Compatibility
STEP 4  -> Baseline Performance
STEP 5  -> Data Quality Audit
STEP 6  -> Robustness Benchmark
STEP 7  -> Determine Required Transformations
STEP 8  -> Apply Targeted Transformation(s)
STEP 9  -> Create New Dataset Version
STEP 10 -> Re-evaluate
STEP 11 -> Programmatic Comparison
STEP 12 -> Save Experiment
STEP 13 -> Generate Final Report
STEP 14 -> Answer User
```

---

## 3.5 IMPROVEMENT REQUEST

Examples:

```
"Improve my dataset."
"Fix the problems in my dataset."
"Improve model performance."
"Handle the detected data-quality problems."
```

This activates an improvement-oriented deterministic workflow.

The agent first determines what problems actually exist.

For example:

```
Data Quality Audit
      |
      +--> Missing values?
      |       -> handle_missing_values
      |
      +--> Class imbalance?
      |       -> balance_data
      |
      +--> Outliers?
      |       -> handle_outliers
      |
      +--> Scaling required?
              -> scale_data
```

Only transformations justified by deterministic observations are allowed.

After every dataset transformation:

```
new version created
    ->
old evaluation invalidated for current version
    ->
performance re-evaluated
    ->
comparison performed
    ->
experiment saved
```

The system MUST NOT blindly apply every available transformation.

---

## 3.6 COMPARISON REQUEST

Examples:

```
"Did SMOTE help?"
"Which version performed better?"
"Compare v001 and v002."
"Was balancing worth it?"
"Did the transformation improve Macro F1?"
```

The system retrieves authoritative experiment/version information.

Comparison calculations are performed by:

```
app/evaluation/comparison.py
```

The LLM may explain the comparison, but does not calculate the metric delta.

Example:

```
v001 Macro F1 = 0.71
v002 Macro F1 = 0.82
```

Python calculates:

```
delta = 0.11
```

Qwen may then explain:

```
"Macro F1 improved by 0.11 after balancing."
```

The number must originate from deterministic data.

---

## 3.7 HISTORICAL / PROJECT MEMORY REQUEST

Examples:

```
"What did we try previously?"
"What happened in the previous experiment?"
"Show my previous experiments."
```

These requests use ChromaDB project memory.

Flow:

```
User
  |
  v
search_project_history
  |
  v
ChromaDB
  |
  v
Relevant historical records
  |
  v
Qwen explanation
  |
  v
User
```

5. AGENT PLANNER DECISION CYCLE
===============================

The AgentPlanner receives:

```
AgentState
+
User Goal
+
Available Tool Definitions
```

Qwen recommends the next action.

Python then verifies:

```
Is this tool available?
Is this action legal in the current state?
Are the required parameters available?
Has this action already been completed?
Is the transformation justified?
Is the current dataset version correctly evaluated?
```

Only legal actions may execute.

Flow:

```
AgentState
    |
    v
Planner
    |
    +---- Qwen recommendation
    |
    v
Python legality check
    |
   / \
legal  illegal
  |       |
  v       v
```

execute  deterministic
fallback
|
v
execute

IMPORTANT:

The deterministic fallback is NOT removed.

It remains the safety mechanism when:

* Qwen is unavailable
* Qwen returns invalid JSON
* Qwen selects an unavailable action
* Qwen selects an illegal action
* planner output cannot be trusted

6. DETERMINISTIC FALLBACK ARCHITECTURE
======================================

The deterministic fallback is state-aware AND request-aware.

It must not assume that every user request means:

```
"Run the entire evaluation."
```

Instead, the current user objective determines the permitted workflow.

Examples:

---

REQUEST:
"What were my baseline metrics?"
--------------------------------

Required state:

```
baseline_metrics
```

If already available:

```
READ baseline_metrics
-> ANSWER
-> COMPLETE
```

If unavailable:

```
inspect_model if necessary
-> inspect_dataset if necessary
-> validate compatibility if necessary
-> evaluate_performance
-> ANSWER
-> COMPLETE
```

STOP.

No automatic transformation.

---

REQUEST:
"Inspect my model and dataset."
-------------------------------

Flow:

```
inspect_model
-> inspect_dataset
-> validate compatibility
-> ANSWER
-> COMPLETE
```

STOP.

---

REQUEST:
"Evaluate my model."
--------------------

Flow:

```
inspect
-> validate
-> baseline
-> data quality
-> robustness
-> targeted transformations
-> re-evaluation
-> comparison
-> experiment
-> report
-> COMPLETE
```

---

REQUEST:
"Improve my dataset."
---------------------

Flow:

```
inspect
-> data quality
-> determine justified transformations
-> transformation
-> new version
-> re-evaluate
-> compare
-> save experiment
-> ANSWER
```

Report generation occurs only when requested or when the improvement workflow
explicitly requires a final report.

9. MODEL EXECUTION
==================

Supported model frameworks:

```
Scikit-learn
PyTorch
ONNX
```

Model loading is handled by:

```
app/models/loader.py
```

Framework-specific execution is handled by:

```
app/models/adapters.py
```

Prediction is handled by:

```
app/models/predictor.py
```

The adapter layer is responsible for converting input data into the format
expected by the loaded model.

For example:

```
sklearn model trained with feature names
    -> DataFrame with matching feature names

sklearn model trained without feature names
    -> NumPy array
```

This prevents unnecessary sklearn feature-name warnings while preserving
correct feature ordering.

================================================================================
11. TRANSFORMATION ENGINE
=========================

Available transformations:

```
handle_missing_values
balance_data
handle_outliers
scale_data
add_gaussian_noise
```

Transformations are NOT automatically applied simply because the tool exists.

The transformation must be justified by observed state.

Examples:

```
missing_values_count > 0
    -> handle_missing_values

class_imbalance_detected = True
    -> balance_data

outliers_count > 0
    -> handle_outliers

model metadata indicates scaling is required
    -> scale_data
```

Gaussian noise is primarily a robustness/benchmarking operation and should
not be treated as ordinary data cleaning.

18. FAILURE HANDLING
====================

If Qwen is unavailable:

```
Request routing uses deterministic fallback classification where possible.
```

If Qwen planner is unavailable:

```
AgentPlanner uses deterministic state-aware fallback.
```

If Qwen produces invalid JSON:

```
Python rejects the decision.
```

If Qwen chooses an illegal action:

```
Python rejects the decision.
```

If a deterministic tool fails:

```
AgentRunner records the failure.
```

Repeated failures of the same action are detected.

After the configured failure threshold:

```
AgentState.status = "failed"
```

The system prevents infinite execution loops.

================================================================================
19. SAFETY AND CORRECTNESS RULES
================================

RULE 1
LLM never calculates numerical ML metrics.

RULE 2
Python determines whether a tool is legal.

RULE 3
Original datasets are immutable.

RULE 4
Every transformation creates a new dataset version.

RULE 5
A transformed dataset must be re-evaluated before its results are treated
as current.

RULE 6
A narrow informational question must not automatically trigger the full
evaluation workflow.

RULE 7
Full evaluation remains available as a deterministic workflow.

RULE 8
Transformations require deterministic evidence.

RULE 9
Historical questions use project memory / experiment history.

RULE 10
Current authoritative state should be preferred over semantic memory when
answering questions about current metrics.

RULE 11
The LLM may explain deterministic results but cannot replace deterministic
calculations.

RULE 12
The deterministic fallback must remain available whenever LLM planning
fails.

User:

    Inspect
    -> Validate
    -> Baseline
    -> Data Quality
    -> Robustness
    -> Transform if justified
    -> Re-evaluate
    -> Compare
    -> Save Experiment
    -> Report

    Inspect Model
    -> Inspect Dataset
    -> Validate
    -> Answer

```

Result:

    Read existing baseline
    OR

    -> Answer
    -> STOP
```

IMPROVEMENT:

```
User:
    "Improve my dataset."

Result:

    Identify problems
    -> Targeted transformation
    -> New immutable version
    -> Re-evaluation
    -> Comparison
    -> Save experiment
    -> Answer
```

HISTORY:

```
User:
    "What did we try previously?"

Result:

    ChromaDB / SQLite history
    -> Retrieve
    -> Qwen explanation
    -> Answer
```

23. FINAL ARCHITECTURAL SUMMARY
===============================

The platform consists of FOUR major decision layers:

```
LAYER 1
--------------------------------------------------------------------------
REQUEST ROUTING

Determines what the user actually wants.

    Information
    Specific action
    Full evaluation
    Improvement
    Comparison
    History


LAYER 2
--------------------------------------------------------------------------
AGENT PLANNING

Qwen recommends the next appropriate deterministic action.

Python validates the recommendation.


LAYER 3
--------------------------------------------------------------------------
DETERMINISTIC EXECUTION

Tools perform:

    inspection
    validation
    evaluation
    transformation
    comparison
    persistence
    reporting


LAYER 4
--------------------------------------------------------------------------
STATE + MEMORY

    AgentState
    SQLite
    ChromaDB
    Immutable dataset versions
    Reports
```

The fundamental execution rule is:

```
USER REQUEST
    ->
DETERMINE REQUEST SCOPE
    ->
SELECT APPROPRIATE FLOW
    ->
USE AGENTSTATE
    ->
QWEN MAY RECOMMEND
    ->
PYTHON VALIDATES
    ->
DETERMINISTIC TOOL EXECUTES
    ->
UPDATE STATE
    ->
STOP WHEN THAT USER'S OBJECTIVE IS SATISFIED
```

The full evaluation pipeline remains the core deterministic backbone.

The major architectural improvement is that the backbone is now selected
according to the user's objective instead of being triggered for every
deterministic or information request.
